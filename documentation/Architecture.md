# Architecture

The plugin hosts the community in a pane, and watches it in the background for new activity.

- `src/app/plugin.ts`: lifecycle, settings (validated on load, persisted through one serialized write path), the view registration, ribbon and commands. It hands the pane a `CommunityViewHost` so the view never touches the plugin instance.
- `src/app/ui/community-view.ts`: the `ItemView`. Toolbar (brand, navigation, shortcuts, open in browser) over a `<webview>` with a persistent partition (`persist:knowii-community`). Welcome card on first open, error card when the community cannot be loaded, browser hand-off on mobile.
- `src/app/domain/community-links.ts`: the only place that knows URLs: base URL normalization, destinations, host check.
- `src/app/domain/community-activity.ts`: pure parsers for the community's web endpoints (`/internal_api/...`: current contact, notification counts and list, chat rooms, unread rooms and threads, threads, spaces), categories, item keys, seen-key bookkeeping. Every response is `unknown` until parsed.
- `src/app/domain/session-cookies.ts`: the stored session: validation, `Cookie` header, `Set-Cookie` merging, sign-in fingerprint (only auth cookie changes trigger a write).
- `src/app/services/community-transport.ts`: three ways to GET as the member. `ElectronSessionTransport` (`remote.session.fromPartition('persist:knowii-community').fetch`, also reads/writes the jar), `HiddenWebviewTransport` (off-screen `<webview>` on the same partition parked on `/robots.txt`, runs `fetch` via `executeJavaScript`), `StoredCookiesTransport` (`requestUrl` with the stored cookies; the only one on mobile).
- `src/app/services/community-client.ts`: one check = current contact, then counts, notifications, room list, unread rooms and threads in parallel, then capped detail lookups (rooms, threads, spaces cached). Tries transports in order; a throw falls through, a 401/204 means signed out.
- `src/app/domain/community-watch.ts`: whole-community watch: parsers for spaces, the activity-sorted feed (`home_page_posts?sort=new_activity`), `post_details` (latest reply per post), chat messages (`messages?previous_per_page=20&next_per_page=0`) and participants; item builders (only after the watch start, the member's own left out, muted spaces out); `roomsToPoll` (unread rooms every check, the others rotating); de-duplication against notifications.
- `src/app/services/activity-inbox.ts`: per-device read and archived keys, and a rolling log (300 items, 14 days) of whole-community items so they stay listed between checks. `merge()` is the watcher's `decorate` hook.
- Writes (`CommunityClient.markRead/archive/markAllRead`): the web app's own endpoints, `PATCH notifications/:id/mark_as_read`, `PATCH notifications/:id/archive`, `POST notifications/mark_all_as_read`, `PATCH chat_rooms/:uuid/mark_as_read`, `POST chat_rooms/mark_all_as_read`, `POST chat_threads/:id/mark_as_read`, `POST chat_threads/mark_all_as_read`, with `X-CSRF-Token` from the `csrf_token` cookie. Every transport implements `send()`.
- `src/app/services/activity-watcher.ts`: the polling loop (setTimeout re-armed after each check, backoff on failures, `checkSoon` on focus, network back, pane navigation), seen-key diffing, first-run backlog.
- `src/app/ui/activity-alerts.ts`, `activity-indicators.ts`, `activity-modal.ts`, `activity-menu.ts`: notices and system notifications, status bar item and ribbon badge, the "what's new" list (recent activity, unread in bold, `is:unread`), the ribbon context menu (unread items, show all, check now, admin pages).
- Admin role: `/internal_api/pundit_users` → `current_community_member.is_admin` (or `roles.admin`), looked up once per member per run and carried on `CommunityMember.isAdmin`. `ADMIN_DESTINATIONS` in `community-links.ts` lists the admin pages; the pane toolbar, ribbon menu and commands only show them to admins.
- `src/app/settings/settings-tab.ts`: declarative settings (Obsidian 1.13+).
- `src/app/whats-new.ts` and `src/app/ui/`: the shared "What's new" tab and support links from the plugin template.

Per-device memory (last page, welcome seen, already-announced item keys) goes through `App.loadLocalStorage` / `saveLocalStorage`, never through `data.json`, so it does not sync with the vault. The session is the exception by design: it lives in `data.json` so it syncs. Session writes skip the UI refresh, and the pane is only re-rendered when a pane setting changes (re-rendering reloads the community). `onExternalSettingsChange` picks up a session synced from another device.
